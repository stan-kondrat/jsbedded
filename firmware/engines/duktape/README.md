# engines/duktape

Adapter for Duktape (Sami Vaarala, MIT). Release 2.7.0, built from the official
release tarball `third_party/duktape-dist/duktape-2.7.0.tar.xz`. The
`third_party/duktape` submodule (https://github.com/svaarala/duktape) pins the
same release (`v2.7.0`, `03d4d72`) for reading the sources and option docs; the
build does not use it. Duktape is a small, easy-to-embed ES5.1 engine with
parts of ES2015+, and it fits every board.

```sh
make firmware BOARD=pico ENGINE=duktape
make firmware BOARD=esp32c3_devkitm ENGINE=duktape
```

## Files

- `engine.cmake`: checks the tarball's SHA-256, extracts `src/` (`duktape.c`,
  `duktape.h`, `duk_config.h`), applies `third_party/patches/duktape/*.patch`,
  appends the option overrides to `duk_config.h`, and compiles `duktape.c` and
  the adapter.
- `duk_config_jsb.h`: the `DUK_USE_*` overrides (below), included at the end of
  the release `duk_config.h`.
- `adapter_duktape.c`: implements [`engine.h`](../include/jsb/engine.h), the
  allocator, `console.log`, and the stack check and fatal handler hooks.
- `sdkconfig.defaults`: the ESP-IDF main task stack (see [Memory](#memory)).

## Sources

Duktape's git tree has no `duktape.c`. Release sources are generated by
`tools/configure.py`, and in 2.7.0 that tooling is Python 2 only. Ubuntu 24.04
(CI) and the ESP-IDF venv have only Python 3, so the build doesn't run it.
Instead it uses `src/` from the release tarball: the same generator's output,
with the default config. The tarball is vendored unmodified, and its checksum
matches the one published with the release. `cmake -E tar` reads `.tar.xz`
itself, so the host needs nothing beyond CMake.

At configure time the files are extracted to `<build>/jsb-duktape-stage/`,
patched there, then copied into `<build>/jsb-duktape/`, replacing only files
whose content changed, so a reconfigure doesn't rebuild `duktape.c`. Editing a
patch or replacing the tarball reruns the configure. A wrong checksum or a patch
that no longer applies fails the configure. Patches, if any, are made against
the release `src/` files and need `git` on `PATH`. There are none today.

## Configuration

The release `duk_config.h` is generated for the default options.
`engine.cmake` appends `#include "duk_config_jsb.h"` to it, so the overrides
come last. Only options that don't change the generated built-in data in
`duktape.c` can be changed this way. Options gated by `present_if` in
`src-input/builtins.yaml` (ES6, ES8, Proxy, buffer objects, Symbol, Reflect,
CBOR, `TextEncoder`/`TextDecoder`, `performance`, coroutines) must stay at
their defaults, because the prebuilt init data refers to their native
functions. Dropping them, or moving built-ins to ROM (`DUK_USE_ROM_*`), needs
`configure.py`.

From upstream `config/examples/low_memory.yaml`, the options that save RAM:

| Option | Effect |
|---|---|
| `DUK_USE_LIGHTFUNC_BUILTINS` | built-in functions are 8-byte lightfunc values instead of ~200 function objects of 70–80 bytes each: about 15 KB less at heap creation. They have no own properties, and their `.name` is generic. |
| `DUK_USE_TRACEBACKS` off | no traceback array on each `Error`. Errors still get `fileName` and `lineNumber`. |
| `DUK_USE_STRTAB_MINSIZE` 128 | the string table starts at 512 bytes (default 4 KB) and grows as needed |
| `DUK_USE_HSTRING_ARRIDX` off, `DUK_USE_LITCACHE_SIZE` off | 4 bytes less per string; no 256-entry literal cache |
| `DUK_USE_HOBJECT_HASH_PROP_LIMIT` 64 | hash part only for objects with 64+ properties (default 8) |
| `DUK_USE_CACHE_ACTIVATION`, `DUK_USE_CACHE_CATCHER` off | no free lists of call records |
| `DUK_USE_VALSTACK_*_SHIFT` off | value stacks grow and shrink exactly, with no spare |

Kept on, although `low_memory.yaml` turns them off, because they cost flash
rather than RAM, or because the contract needs them:
`DUK_USE_VERBOSE_ERRORS` (error messages), `DUK_USE_AUGMENT_ERROR_CREATE`,
`DUK_USE_PC2LINE` and `DUK_USE_FUNC_FILENAME_PROPERTY` (file and line of
errors), the JSON/array fast paths and all built-ins.

From `config/examples/shallow_c_stack.yaml`, recursion limits for small C
stacks: native calls 60 (default 1000), compiler 50 (2500), RegExp
compiler/executor 100 (10000), JSON encode/decode 100 (1000), mark-and-sweep 32
(256). Beyond these, `DUK_USE_NATIVE_STACK_CHECK` calls
`jsb_duk_native_stack_check()`, which throws `RangeError` once calls have used
`JSB_DUKTAPE_STACK_LIMIT` bytes of C stack below `jsb_engine_eval()`.

`DUK_USE_FATAL_HANDLER` and the heap's fatal handler print
`JSBedded: Duktape fatal error: <msg>` and call `abort()`. Duktape requires that
fatal handlers don't return. With every call protected, fatal errors only come
from internal failures such as running out of memory where Duktape cannot throw.

The date provider is the release's generic fallback for bare-metal toolchains:
`time()` and `gmtime()`, with one-second resolution. Until something sets the
clock, that is time since boot. arm-none-eabi, xtensa-esp-elf and
riscv32-esp-elf define none of the `__unix__`/`__linux`/`__posix` macros
`duk_config.h` checks, so they all get this fallback. It uses only C89 calls
(`time`, `gmtime`, `localtime`, `mktime`) and standard `struct tm` fields: no
`tm_gmtoff`, `gettimeofday`, `clock_gettime`, `strptime` or `strftime`.
`duktape.c` uses no pthreads or `malloc_usable_size()` either (the newlib gaps
QuickJS needed patches for). On pico-sdk, newlib's `time()` goes through the
SDK's `_gettimeofday()`.

`duktape.c` is compiled with `-Os` and `-w` (`COMPILE_FLAGS`), so upstream
warnings can't fail ESP-IDF's `-Werror=all`. The adapter keeps the platform's
warnings. `m` is linked for the math functions.

## Globals

The standard Duktape 2.7 set (ES5.1 built-ins, `Duktape`, typed arrays,
`Proxy`, `Reflect`, `Symbol`, `CBOR`, `TextEncoder`/`TextDecoder`,
`performance`) plus the global below. The language is ES5.1 with parts of
ES2015+: there are no arrow functions, classes or Promise.

| Global | Behaviour |
|---|---|
| `console.log(...)` | arguments converted to strings, separated by spaces, then `\r\n`, via `jsb_hal_console_write()` |

Uncaught exceptions print `Uncaught <Name>: <message>` and, when Duktape
recorded them, `    at <file>:<line>`, with `\r\n` line ends.
`jsb_engine_eval()` then returns -1. Syntax errors also carry the line in the
message, for example `SyntaxError: unterminated string (line 1)`. Duktape 2.7
has no Promise or job queue, so there are no pending jobs to run.

`jsb_engine_eval()` compiles straight from `(source, len)` (no NUL needed, and
the source is not kept on the heap). It runs the script as global code in a
protected call.

## Memory

The adapter's allocator puts an 8-byte size header on each block it gets from
`malloc()`. That lets it enforce the limit without `malloc_usable_size()`. At
the limit an allocation fails, Duktape runs an emergency mark-and-sweep and
retries, and if that is not enough the operation throws `RangeError`. Per board,
from `engine.cmake`:

| Board | SRAM | JS heap limit | C stack for Duktape calls |
|---|---|---|---|
| pico (RP2040) | 264 KB | 96 KB | 12 KB |
| pico_w (RP2040) | 264 KB | 80 KB (room for CYW43 + lwIP) | 12 KB |
| pico2 (RP2350) | 520 KB | 256 KB | 12 KB |
| pico2_w (RP2350) | 520 KB | 224 KB (room for CYW43 + lwIP) | 12 KB |
| esp32s3_devkitc | 512 KB (~380 KB free heap) | 192 KB | main task stack − 4 KB |
| esp32c3_devkitm | 400 KB (~300 KB free heap) | 128 KB | main task stack − 4 KB |

The limits are ceilings, not reservations: Duktape frees memory through
reference counting as soon as values die, so it only holds what scripts keep.

Memory use is estimated, not measured. Upstream puts the RAM-built-in function
objects alone at 14–16 KB, which lightfuncs remove. An empty heap with these
options is estimated at 25–40 KB on 32-bit targets.

### C stack

Duktape's compiler and native calls recurse on the C stack (calls between
ECMAScript functions don't). The recursion limits above bound the depth, and the
stack check turns the remaining cases into `RangeError`. The compiler is bounded
only by its recursion limit, so the stack limit keeps 4 KB of margin.

- **pico-sdk:** the core 0 stack starts at the top of SCRATCH_Y and grows down
  through SCRATCH_X (unused without core 1), 8 KB in all. Below that it runs into
  the top of main RAM, where the heap ends. pico-sdk reserves only
  `PICO_STACK_SIZE` (2 KB) and has no stack guard by default. With the heap
  limits above, newlib's heap stays far below the top of RAM, so 12 KB of stack
  is free in practice, but the linker does not reserve it. pico-sdk panics on a
  failed `malloc()` (`PICO_MALLOC_PANIC`); the JS limit keeps Duktape well
  inside the heap.
- **ESP-IDF:** Duktape runs on the main task. `sdkconfig.defaults` in this
  folder raises `CONFIG_ESP_MAIN_TASK_STACK_SIZE` from 3584 bytes to 16 KB, and
  `engine.cmake` gives Duktape that size minus 4 KB. `hal/esp-idf/platform.mk`
  applies the file after `hal/esp-idf/sdkconfig.defaults`. Duktape (estimated
  200–300 KB of code) fits the default 1 MB factory partition.

## Boards

Expected to work on all six: **pico, pico_w, pico2, pico2_w, esp32s3_devkitc,
esp32c3_devkitm**. `unsupported_boards` is empty. Flash use (estimated
200–300 KB) and RAM use (estimated 25–40 KB empty) fit every board.
`min_flash_kb` and `min_ram_kb` stay `null` until measured (`bench/`).
